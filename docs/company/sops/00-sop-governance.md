## 1. 目的与权限边界

本规范用于建立一套轻量、可复核、不过度扩张的公司 SOP 体系。SOP 的作用是把**已经批准的重复工作**固化为一致步骤、证据和停止条件；它不制定公司战略，也不创造新的预算、发布、部署、付款、采购、外联、广告、账号操作或商品状态权限。

- SEO/GEO 仍是公司唯一 P0。SOP 建设只做支持当前 P0 或降低重复执行风险所需的最小工作，不与业务交付争夺优先级。
- 不新增永久运营部门。秘书处或 14 天运营执行台可以维护任务队列、证据和未来总索引，但不是新的决策层。
- SOP 中写有某项操作，不等于该操作已经获授权；执行时仍须满足对应权威文件、批准记录和环境权限。
- 未知事实写“待确认”。计划、草稿、代码存在、截图、测试数据或内部验收不得冒充已部署、已发布、已产生业务结果或已取得外部授权。
- 本规范不自动改变既有 SOP 的执行状态。既有文件须在未来总索引中补齐 Owner、版本、状态、复盘日期与批准依据后，才能按本规范声称为 `active`。

## 2. 何时应建立 SOP

满足下列任一条件时，可以提出 SOP：

1. 同一流程预计重复执行，且步骤、输入和完成证据可以稳定复用。
2. 流程跨两个或以上责任会话，需要固定交接字段、验收人或停止条件。
3. 错误会影响客户、品牌、商品事实、测量口径、生产系统、付款、履约、隐私或合规。
4. 现有执行反复出现漏项、状态误报、证据丢失或责任不清。
5. 创始人、CEO 或拥有该事项既有权限的责任人明确要求固化流程。

通常不建立 SOP 的情形：一次性研究、尚未批准的策略设想、仍在探索且步骤频繁变化的实验、单纯知识说明、仅需几个核对项的低风险任务。此类事项优先使用 brief、计划、决策记录或 checklist。

## 3. SOP 与 checklist 的区别

| 项目 | SOP | Checklist |
| --- | --- | --- |
| 解决的问题 | 规定何时启动、由谁执行、按什么顺序、如何验收和何时停止 | 防止一次执行漏掉已知检查项 |
| 必含内容 | 适用条件、Owner、输入、步骤、输出、证据、异常/停止条件、审批边界、复盘日期 | 检查项、通过标准、结果、检查人和日期 |
| 是否规定流程顺序 | 是；若可并行必须明确 | 通常不规定，除非勾选顺序本身有风险 |
| 是否单独授权 | 否 | 否 |
| 适用状态 | 受本规范五态管理 | 作为 SOP 附件或独立审核工具；不得越过其上位 SOP/决策 |
| 完成含义 | 有执行证据证明流程和验收条件均满足 | 只证明列出的检查项已核对，不自动证明整项工作完成 |

当一个 checklist 同时开始规定角色、输入、顺序、异常升级和放行条件时，应升级为 SOP；当 SOP 的一段只包含可勾选验收项时，应保留为其附属 checklist，避免复制一套平行流程。

## 4. 编号、文件名与责任字段

### 4.1 编号

- 文件名采用 `NN-kebab-case-title.md`，SOP ID 为 `SOP-NN`。
- `00` 保留给本治理规范；未来总索引建议使用 `01-sop-index.md`，但本轮不创建。
- 其他编号是稳定排序键，不代表新增部门、汇报层级或优先级。现有 `20-*`、`30-*` 文件保持兼容。
- 新 SOP 使用尚未占用的两位编号；需要在相近主题间插入时可使用空余编号，不因排序调整而改动已有 SOP ID。
- SOP ID 一经进入 `ready` 不再复用。`retired` 文件保留原 ID；替代流程取得新 ID，并互相记录前任/继任关系。
- 独立 checklist 使用 `CHK-NN`；作为某 SOP 的附件时使用 `SOP-NN / CHK-A`、`CHK-B`，不另造审批权限。

### 4.2 每份 SOP 的必填元数据

每份 SOP 顶部必须明确：

- `SOP ID`、标题和适用范围；
- 唯一 Owner，以及需要参与验收的 reviewer；
- 版本、状态、生效日期和下一次复盘日期；
- 上位决策或权威文件；
- 前任/继任 SOP（没有则写“无”）；
- 证据保存位置与敏感信息边界。

Owner 对内容准确性、状态、复盘和证据完整性负责，但不会因成为 Owner 自动获得执行外部动作或高风险变更的权限。Owner 暂缺时填写“待确认”，该 SOP 不得进入 `active`。

## 5. 版本规则

- `v0.x`：`draft` 或 `ready` 阶段；仍可调整结构，不能称为生效流程。
- `v1.0`：首次获准进入 `active` 的版本。
- 小版本升级（如 `v1.1`）：不改变权限、适用范围、关键步骤、通过标准或停止条件的澄清、链接修复和证据字段完善。
- 大版本升级（如 `v2.0`）：改变适用范围、角色责任、关键步骤、放行/停止条件、生产或客户影响、证据强度或审批边界。

任何正在 `active` 的 SOP 若发生大版本变更，必须先把新版本置为 `ready` 并重新批准；旧版本在新版本生效前继续有效，除非因风险被明确 `paused`。不得静默覆盖生效版本或删除历史审计记录。

## 6. 五态与流转

| 状态 | 含义 | 可执行范围 | 进入下一状态的最低条件 |
| --- | --- | --- | --- |
| `draft` | 正在起草，字段或证据可不完整 | 仅内部编写和评审，不作为执行依据 | Owner、范围、步骤、证据、停止条件和审批边界完整后进入 `ready` |
| `ready` | 内容完整，等待拥有既有权限的批准人确认 | 可做桌面演练或隔离环境验证；不得据此执行未授权外部动作 | 批准人、版本、生效日、复盘日和验证证据齐备后进入 `active` |
| `active` | 已批准并在所列范围内生效 | 仅执行 SOP 与既有授权共同允许的动作 | 到期复盘后继续、更新、`paused` 或 `retired` |
| `paused` | 因阻塞、风险、权限缺失或优先级暂停，暂时不可继续 | 保留文档与证据；只允许消除阻塞所需的已授权内部准备 | 原批准人或拥有同等权限者确认新证据和恢复范围后回到 `active`/`ready` |
| `retired` | 已取消、失效或被新 SOP 替代 | 只读留档，不再执行 | 不恢复原 ID；需要恢复时建立新版本或继任 SOP |

允许的标准流转为：`draft → ready → active → paused/retired`；`paused → ready/active/retired`。发现安全、法律、商品事实、客户、支付、隐私或生产风险时，Owner、执行人或 CEO 可立即暂停执行并保留证据；恢复仍须由原批准边界内的授权人确认。

## 7. 变更与审批边界

### 7.1 不需要新增决策的维护

在不改变行为和权限的前提下，Owner 可提出并由既有 reviewer 复核：错字、格式、失效内部链接、示例澄清、证据字段补充。变更后增加小版本号和变更记录。

### 7.2 必须重新批准的变更

出现以下任一项时，SOP 回到 `ready`，由拥有该事项**既有权限**的批准人重新确认：

- 适用对象、市场、渠道、系统、Owner 或责任分工变化；
- 新增、删除或重排关键步骤；
- 通过标准、证据强度、停止条件或异常处理发生变化；
- 影响客户可见内容、生产环境、数据口径、商品事实、订单、支付、履约、隐私或合规；
- 从内部准备扩大为外部执行。

### 7.3 始终需要单独明确授权的动作

任何 SOP 都不能替代下列授权：公司策略或 P0 变化、预算、广告、生产部署、公开发布、DNS/canonical/切域、外部账号写入、付款、采购、供应商/货代或其他外联、客户数据访问、订单/支付处置、商品价格/库存/`isActive`/可见性/加购/结账状态变化。执行前应回到对应决策与权限链，不得由 SOP Owner 自批。

## 8. 证据要求

每次 SOP 执行至少记录：

1. SOP ID、版本、执行日期/时区、执行人和 reviewer。
2. 适用对象与范围，例如 URL、内容 ID、SKU、环境或数据窗口；不保存客户个人数据或支付标识。
3. 输入来源及其版本/取得时间；缺失项写“待确认”。
4. 关键步骤的真实结果，包括失败、跳过、阻塞和例外，不只记录最终结论。
5. 可复核证据位置，例如仓库文件、测试输出、平台聚合截图、批准记录或外部权威来源；敏感值必须脱敏且不得写入公司文档。
6. 验收条件逐项结果、复核人、复核时间和结论。
7. 后续动作、失效触发条件和下一复盘日期。

以下内容不能单独作为完成证据：计划、待办、口头转述、无日期截图、代码或配置存在、按钮可见、测试订单、模板已填写、候选素材、粗剪、条件 GO，或缺少版本/环境/对象映射的测试结果。

证据不足时，状态保持原样或转为 `paused`；不得为了完成率补写数据、放宽门槛或把 `ready` 解释成 `active`。

## 9. 每份 SOP 的最小正文结构

1. 目的与适用/不适用条件；
2. Owner、参与者、reviewer 与权限边界；
3. 启动输入和前置条件；
4. 按顺序或明确并行关系的执行步骤；
5. 输出物和完成定义；
6. 证据记录方式；
7. 异常、停止、恢复与升级路径；
8. 版本变更记录和复盘结果。

缺少任一项时只能保持 `draft`，除非该项明确写“不适用”并给出理由。

## 10. 未来总索引字段

未来 `docs/company/sops/01-sop-index.md` 应每个 SOP 一行，至少包含：

| 字段 | 用途 |
| --- | --- |
| SOP ID / 类型 | 唯一编号；区分 SOP 与 checklist |
| 标题 / 文件路径 | 可读名称与唯一仓库位置 |
| 主题分组 | 排序和检索用途，不代表部门或优先级 |
| Owner / reviewer | 唯一责任人及验收角色 |
| 状态 / 版本 | 五态之一及当前有效版本 |
| 适用条件 / 风险级别 | 何时使用，以及错误影响范围 |
| 上位决策 / 批准人 | 该流程依据与既有授权来源 |
| 生效日期 / 下次复盘日期 | 当前版本的有效窗口 |
| 证据位置 | 最近一次可复核执行或验证记录 |
| 依赖 / 前任 / 继任 | 关联流程、替代关系和阻塞 |
| 最近更新 | 日期、变更人和变更摘要 |

总索引只汇总状态，不复制 SOP 正文，不把 `ready`、`paused` 或证据缺失的流程写成已执行。索引维护可由秘书处或试点执行台承担；状态批准、优先级和外部权限仍属于现有决策链。
